# ACADEMe roadmap index

These roadmaps describe future work by workstream. They are planning
documents, not permission to implement. The execution checklist and current
status remain in `../../tasks/roadmap.md`.

## Workstreams

| Roadmap | Scope | Status |
|---|---|---|
| [Automation](automation.md) | Support triage, GitHub issues, agent-created draft PRs | Planned |
| [Infrastructure](infrastructure.md) | Hosting, deployment, databases, secrets, backups, reliability | Planned |
| [UI](ui.md) | Screens, journeys, design system, accessibility, UI testing | Planned |
| [Backend](backend.md) | API, domain features, persistence, contracts, migrations | Planned |
| [AI and Pebby](ai.md) | Provider bundle, prompts, safety, evaluation, cost controls | Planned |
| [Telemetry](telemetry.md) | Logs, metrics, traces, errors, product events, retention | Planned |

## Roadmap rules

- A roadmap records intent, dependencies, decisions, and gates.
- An implementation task belongs in `../../tasks/` after approval.
- A roadmap must link to the rule or spec that governs its work.
- Do not put credentials, raw student content, or generated provider payloads in
  roadmap files.
- Mark a roadmap item as decided only after the decision is recorded in the
  relevant spec or project decision log.
